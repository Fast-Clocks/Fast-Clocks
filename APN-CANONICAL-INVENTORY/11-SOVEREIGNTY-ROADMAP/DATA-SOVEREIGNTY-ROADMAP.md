# DATA-SOVEREIGNTY ROADMAP — Current vs Future Backend

Supabase (`apn-backbone-sydney`, ap-southeast-2) is the **current** platform, **not** the permanent or complete sovereignty solution. This roadmap keeps APN and future customers in control if Supabase becomes unsuitable, a region/provider changes, a customer requires self-hosting, or APN stops operating and verification must continue independently.

Everything below is **PLANNED / PROPOSED**. Nothing here is deployed.

## Phase gates

### PHASE 0 — DOCUMENT AND STABILISE  *(this inventory)*
- Objective: a truthful, evidence-based backend map + risk register (done by this pass).
- Deliverables: source report, schema/RLS/edge/cron registers, ledger assessment, risk register.
- Approval gate: Chris accepts the inventory as the canonical backend record.

### PHASE 1 — INDEPENDENT BACKUP AND RESTORE
- Objective: encrypted off-platform backups of schema + data + ledger, with tested restore.
- Prereqs: storage target outside Supabase (AU-resident); backup keys in customer custody.
- Deliverables: scheduled `pg_dump`/logical backup, checksum manifest, restore runbook, **ledger-chain re-validation after restore** (recompute hashes, confirm continuity).
- Risks: backup exfiltration (mitigate: encryption at rest + key separation).
- Approval gate: first successful restore-and-verify on a scratch project.

### PHASE 2 — VENDOR-NEUTRAL RECEIPTS AND VERIFIER  *(unblocks the product claim)*
- Objective: a receipt/verification format that is reproducible **without APN infrastructure**.
- Prereqs: FIND-004 fixed — canonical serialisation + `hash_version` + documented field order.
- Deliverables: published hash spec, a tiny offline verifier (recompute chain from exported rows), portable proof bundle (rows + spec + verifier).
- Risks: format churn breaking old receipts (mitigate: versioned spec, never mutate historical rows).
- Approval gate: an exported ledger slice verifies on a clean machine with no network.

### PHASE 3 — PORTABLE POSTGRES DEPLOYMENT
- Objective: stand the schema up on plain PostgreSQL (no Supabase-only dependency in the core).
- Prereqs: inventory of Supabase-specific pieces (`auth.uid()`, `pg_net`, Edge Functions, storage, `app.settings` GUCs) and portable replacements.
- Deliverables: portable migration set; documented shims for auth + scheduled jobs + object storage.
- Risks: RLS depends on Supabase `auth`; needs an auth adapter.
- Approval gate: schema + ledger run on vanilla Postgres in CI.

### PHASE 4 — CUSTOMER-CONTROLLED HOSTING
- Objective: a customer can run their own database / dedicated instance.
- Deliverables: per-customer deployment template; data-residency options; export/import.
- Approval gate: one dedicated customer instance provisioned and verified.

### PHASE 5 — FULL SOVEREIGN DEPLOYMENT OPTIONS
- Objective: APN-operated AU deployment · dedicated customer DB · customer-controlled cloud · self-hosted Postgres · offline/local verification · hybrid.
- Cross-cutting: **key ownership** (offline root/policy key never in the app; online issuer key in KMS/HSM; customer-owned/co-signing keys optional), **evidence separation** (private source evidence vs public-safe proofs vs controlled disclosure), **retention & erasure** (erase source PII while retaining tombstone/revocation events that preserve chain integrity), **disaster recovery** (region failure, provider failure, loss of APN control plane, verifier availability via portable bundles).

## Current-vs-future backend summary
- **DEPLOYED:** resource hub, domain register + watch, link-audit, four-machine `apn_ledger_events` spine, inbox v0 schema.
- **PARTIALLY DEPLOYED:** public verifier (fns exist, not anon-exposed), contributor wall / resource_register views (not wired to anon).
- **PLANNED:** independent backups, vendor-neutral verifier, portable/self-hosted deployment, customer keys.
- **UNVERIFIED / ELSEWHERE:** the Sovereign-Engine `ledger_entries`/`verification_records`/Merkle/Ed25519 model (APN Ledger Trust — not in this account).
